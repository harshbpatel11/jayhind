# Production deployment

A merge (push) to `production` in a service repo deploys that service. Nothing
else does. There is no Docker and no container registry: GitHub Actions builds,
rsyncs the result to the host, and a script on the host switches it live.

| Domain | Service | Repo | Internal port | Runs as |
|---|---|---|---|---|
| aakhaja.com | client-front | jayhind-client-front | 4300 | nginx static |
| api.aakhaja.com | client-back | jayhind-client-back | 3000 | pm2 |
| hub.aakhaja.com | admin-front | jayhind-admin-front | 4500 | nginx static |
| apihub.aakhaja.com | admin-back | jayhind-admin-back | 3100 | pm2 |

The OCR sidecar is **not deployed**. admin-back's `/health/ready` therefore
answers 503 (`ocrSidecar` down); `/health/live` is what the deploy checks.

## How a deploy works

```
push to production
  └─ .github/workflows/deploy-production.yml  (in the service repo)
       npm ci → npm test (backends) → build
       rsync → /srv/jayhind/<service>/releases/<UTC-timestamp>-<sha>/
       ssh   → /srv/jayhind/bin/jayhind-deploy <service> <release>
                 backend:  link shared/.env, logs, uploads, tmp (+ client-back's
                           site-configuration-assets) → npm ci (or reuse the live
                           release's node_modules if the lockfile is unchanged)
                           → sequelize db:migrate → swap `current` → pm2 restart
                           → /health/live, else swap back and fail the workflow
                 frontend: swap `current` → GET / on its port, else swap back
                 prune to the newest 5 releases
```

Builds run on the runner because the host has ~1 GB RAM (+2 GB swap): an
Angular production build does not fit. Each repo's workflow uses its own
`concurrency` group, so a second push queues behind the first rather than
cancelling it mid-migration.

⚠️ **Migrations run before the switch and are not rolled back** if the new
process then fails its health check. They are forward-only by design (CLAUDE.md
§4.8), so a failed deploy leaves the previous release serving a schema one step
ahead. Write migrations that the previous release tolerates.

⚠️ **Cross-service contract changes** (`/internal/*`, `/api/v1/*`, licence
flags, CLAUDE.md §12) deploy per repo, not atomically. Merge the side that
accepts both shapes first.

## Host layout

```
/srv/jayhind/
  bin/jayhind-deploy          ← _ops/deploy/jayhind-deploy.sh
  ecosystem.config.js         ← _ops/deploy/ecosystem.config.js
  <service>/current           → releases/<id>
  <service>/releases/<id>/
  <service>/shared/           .env, uploads/, logs/, tmp/ — never overwritten
/etc/nginx/sites-available/jayhind.conf, snippets/jayhind-*.conf
/etc/nginx/conf.d/cloudflare-realip.conf   Cloudflare ranges (regenerated by bootstrap)
/etc/nginx/ssl/aakhaja.com.{crt,key}       self-signed origin cert (10 years)
```

`.env` files exist **only** on the host (`shared/.env`, mode 600). They are not
in any repo and no workflow writes them. `INTERNAL_SERVICE_KEY` is identical in
both. Both backends set `TRUST_PROXY=loopback`, which is what gives the per-IP
rate limit a real client IP behind nginx.

Database: MySQL (OCI) at `10.0.1.12`, databases `jayhind_client` and
`master_hub`. Not reachable from GitHub runners, which is why migrations run on
the host.

## Cloudflare

All four names are proxied (orange cloud). The origin serves 443 with a
self-signed certificate plus 80, so SSL mode **Full** works (and Flexible,
though that sends plaintext between Cloudflare and the host). For **Full
(strict)**, create a Cloudflare Origin Certificate for `aakhaja.com,
*.aakhaja.com`, overwrite `/etc/nginx/ssl/aakhaja.com.crt` / `.key`, and
`sudo nginx -t && sudo systemctl reload nginx`. Turn on **Always Use HTTPS** in
Cloudflare; the origin deliberately never redirects (under Flexible that loops).

Requests to the raw IP, or for any other Host, get no response (`return 444`).

## GitHub secrets (each of the four service repos)

| Secret | Value |
|---|---|
| `PROD_HOST` | the host's public IP |
| `PROD_SSH_KEY` | private key of the `github-actions-deploy@jayhind` ed25519 key (in `authorized_keys` for `ubuntu`) |
| `PROD_KNOWN_HOSTS` | `<ip> ssh-ed25519 …` lines taken from the host's `/etc/ssh/ssh_host_*_key.pub`, pinned rather than `ssh-keyscan`ned at run time |

To revoke CI's access, delete that key's line from `~ubuntu/.ssh/authorized_keys`.

## Common operations

```bash
# status / logs
pm2 ls
pm2 logs client-back --lines 100
tail -f /srv/jayhind/client-back/shared/logs/logNest/*.log

# redeploy the same commit: GitHub → Actions → Deploy production → Run workflow

# manual rollback to the previous release (backend)
cd /srv/jayhind/client-back
ls releases                               # pick an id
ln -sfn releases/<id> current.tmp && mv -Tf current.tmp current
pm2 restart client-back --update-env
# frontends: the same two lines, no pm2

# change configuration
nano /srv/jayhind/admin-back/shared/.env && pm2 restart admin-back --update-env
```

## Setting up a host from scratch

```bash
scp -r _ops/deploy ubuntu@<host>:/tmp/jayhind-deploy
ssh ubuntu@<host> 'bash /tmp/jayhind-deploy/server-bootstrap.sh'
```

The bootstrap script is idempotent. It adds swap, installs pm2 (boot service +
log rotation), creates `/srv/jayhind`, installs the deploy script, the pm2
config, the nginx site and the origin certificate. Changing any file in this
directory takes effect **only after it is re-run** — the workflows call the
installed copy.

Then, once:

1. Create both databases (`utf8mb4`, `utf8mb4_0900_ai_ci`).
2. Write `/srv/jayhind/{client-back,admin-back}/shared/.env` from each repo's
   `.env.example` (`NODE_ENV=production`, `TRUST_PROXY=loopback`, the DB, one
   shared `INTERNAL_SERVICE_KEY`, a separate `JWT_SECRET` each, `ALLOWED_ORIGINS`
   = the frontend's `https://` origin, `MASTER_URL=http://127.0.0.1:3100`,
   `CLIENT_API_URL=http://127.0.0.1:3000`).
3. Deploy **client-back first** — its migrations create `companies`, which
   admin-back's second connection reads.
4. Seed once, from each `current/`:
   `NODE_ENV=production SEED_DEFAULT_PASSWORD='<strong>' npx --no-install sequelize db:seed:all`
   (admin-back: super-admin `admin`, HSN master, plans; client-back: geo data).
   Seeders are **not** part of a deploy.
